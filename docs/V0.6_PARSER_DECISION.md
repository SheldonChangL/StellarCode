# v0.6 parser decision: extend the current scanner or adopt Tree-sitter

**Decision: extend the current deterministic scanner.** Tree-sitter is not adopted for v0.6. This can be revisited if the measured failures below appear in development diagnostics.

## What v0.6 actually needs

From [V0.6_CURRENT_GRAPH_GAPS.md](V0.6_CURRENT_GRAPH_GAPS.md), the facts to extract per file are:

- call sites inside a known symbol range: `f(…)`, `recv.m(…)`, `this.f.m(…)`, `self.f.m(…)`
- identifier arguments of a call (registration)
- class heritage (`extends`/`implements`, Python bases)
- constructor field bindings: `this.x = p`, TS parameter properties, typed class fields, `self.x = p`, `self.x = Cls()`
- re-exports
- Python import aliases

The hard part of v0.6 is **cross-file resolution**: binding → module → original declaration → field type → class → member, and uniqueness under interfaces. That happens over the whole index in `rebuildEdges`, and no parser does it for us.

## Comparison

| Criterion | Extend current scanner | Tree-sitter (`web-tree-sitter` + grammars) |
|---|---|---|
| JS/TS member calls | Masked text (comments and strings blanked, offsets preserved) plus balanced-bracket scanning finds `a.b.c(` call sites and their argument lists reliably. Chained or computed calls (`a[b]()`, `f()()`) are deliberately skipped. | Exact syntax tree, including chains and computed members |
| Python calls | Indentation blocks already give symbol ranges, and call sites are found on masked lines. Decorators, `self.x` assignments and `from … import … as` are line-local. | Exact |
| Ranges | Existing symbol ranges are reused. Call-site lines are exact because masking preserves offsets. | Exact node ranges |
| Aliases and re-exports | Import and export statements are already regex-parsed; extending that to `export … from` is small. | Requires the same resolution code on top of the tree |
| Type and receiver resolution | Not provided by either. Built in the resolver from declared field and parameter types, constructor assignments and unique members. | Not provided. Same resolver work. |
| Performance | No extra pass: it runs on the masked text the parser already builds. | WASM init plus a parse per file. Fine at this scale, but a new cost with no resolution benefit. |
| Dependency size (measured with `npm view` on 2026-11-05) | **0 dependencies** (unchanged; the package has no runtime dependencies today) | `web-tree-sitter` 0.27.1: 4.7 MB unpacked, plus grammar packages (`tree-sitter-typescript`: 38.8 MB unpacked including sources; prebuilt `.wasm` per language). The native `tree-sitter` binding needs node-gyp. |
| Incremental parsing | Not needed: only changed files are re-parsed today, and resolution is a global pass over stored facts. | Incremental edit trees help editors, not a batch indexer keyed on content hashes |
| Maintenance | One file of extraction rules, covered by synthetic tests. The failure mode is a *missed* fact, which yields no edge. | Grammar and ABI version pinning across languages, a WASM loading path, and per-language query files |
| Unsupported languages | The scanner indexes only JS/TS and Python today; capability metadata marks each indexed language | Same requirement |

## Why not Tree-sitter now

- **It would make no relation resolvable that the scanner cannot already see.** Its gain is syntactic completeness: chained calls, computed members, exotic formatting.
- **v0.6 deliberately does not emit edges for those shapes.** Dynamic and computed calls produce no edge by design. The precision rule is "unresolvable means no edge", so a missed syntactic fact costs recall, never correctness.
- **No measurable reason exists yet.** The rule for adopting it is "clear measurable reason". If the development diagnostics show required edges missed *because of syntax extraction*, rather than resolution, that becomes the measurable reason to revisit.
- **Zero runtime dependencies is a product property worth keeping** for a local, zero-token indexer.

## Guardrails for the scanner extension

- Extraction runs on masked text, so it never matches inside strings or comments.
- Facts carry exact lines, and every edge records its evidence line and expression.
- Shapes that are not recognized produce **no fact**. There is no fuzzy matching and no name-only cross-file guessing.
- Language capability is explicit, and every indexed file carries one value:
  - `semantic` for JS/TS (`.ts .tsx .mts .cts .js .jsx .mjs .cjs`)
  - `semantic-partial` for Python: receiver resolution is conservative
- Other languages are not indexed at all (`SUPPORTED_EXTENSIONS`), so they report no semantic edges instead of silently claiming support.
