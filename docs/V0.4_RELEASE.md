# StellarCode v0.4 — Universe UX Rewrite + Architecture Classification

v0.4 replaces the MVP's flat dependency-cloud presentation with a hierarchical code universe designed for real repositories with hundreds of files.

## What changed

### Galaxy-first navigation

The default canvas no longer renders every file and relation at once.

1. **Galaxy** — top-level repository areas such as `src`, `tests`, `scripts`, `infra`.
2. **Module** — logical systems inferred from directories such as `src/lib/llm`, `src/actions`, `tests/e2e`.
3. **File** — local files inside one selected module.

This keeps the overview readable even when the repository contains hundreds of files.

### Graph-on-demand

Global dependency edges are hidden by default. Relations appear only when they are useful:

- hover a file: preview its local neighborhood;
- select a file: show direct dependency energy links;
- cross-module dependencies appear as dashed external satellites;
- Impact mode expands only reverse-dependency reach and dims unrelated files.

### Architecture classification

Each indexed file is deterministically classified as one of:

- `application-entry`
- `module-entry`
- `domain-core`
- `service`
- `ui`
- `infrastructure`
- `test`
- `config`
- `docs`
- `source`

Classification uses path conventions plus `package.json` entry/run hints. A nested `src/lib/llm/index.ts` is now a **Module Entry**, not an application entry.

### New CLI/MCP surface

```bash
stellar architecture
```

returns application entries, representative structural core files, galaxy/module summaries and role counts.

MCP now also exposes:

```text
stellar_architecture
```

### Architecture context ranking

For questions such as:

```text
找出這個專案的主要入口與核心模組
```

StellarCode now chooses:

1. a real application entry where one can be identified;
2. structurally important files from distinct modules;
3. related dependencies.

Nested barrel `index.ts` files no longer dominate simply because their basename is `index`.

### CLI polish

The installed `stellar` binary now filters only Node's `node:sqlite` ExperimentalWarning. Other Node warnings remain visible.

## Compatibility

Existing `.stellar/project.json` and per-project `index.db` files remain compatible. v0.4 does **not** require deleting or reinitializing existing projects.

Architecture roles and hierarchy are derived at query time from existing indexed metadata, so a new full scan is not required solely for the v0.4 UI/classification update.
