# v0.5.5 — Context Precision + Benchmark Intent

v0.5.5 does not change the correctness architecture of v0.5.4. It changes what
`stellar context --compact --with-source` spends its source budget on, and it makes the
benchmark measure task types honestly.

Goal: return the smallest grounded source set that explains the requested behavior, not
the smallest source set at any cost.

## Deterministic intent model

`src/query/intent.js` exports `classifyIntent(prompt)`:

```json
{ "intent": "flow", "confidence": 1, "signals": ["flow:trace"], "signalWords": ["trace"] }
```

| Intent | Meaning | Typical signals |
|---|---|---|
| `navigation` | locate an implementation, entry point or owner | default; find / where / owns / defined |
| `flow` | trace execution across modules | trace, flow, from … to, integrated into, consumes, transition |
| `impact` | what depends on / changes because of something | impact, affected, would break, depends on, what uses, "if X changes" |
| `editing-prep` | prepare to modify code | modify, change, add, adjust, refactor, "before adding/changing …", "I need to …" |

Each intent sums weighted regex signals. A score of 3 decides; ties go to the more specific
intent (`impact` > `editing-prep` > `flow`). The classifier uses only the prompt text: no
LLM, no repository state, no task id, no expected files. CLI, MCP and the benchmark use
the same function.

`implementation` / `implemented` are descriptive and never count as editing signals.

The words that matched a signal (`signalWords`, filtered to question-shape vocabulary such
as "consumes", "transition", "defined") are discounted to 30% weight as code evidence, so
"the interface it consumes" does not rank a `consume()` method.

## Context precision pipeline

```
query → intent → candidate files → symbols inside each file → relation evidence
      → source-range selection → fair budget allocation → dedup
```

### Query terms

- Hyphenated phrases are split ("end-of-cleaning" → end, cleaning) and terms are lightly
  stemmed (finishing → finish, applies → apply).
- Terms are weighted by inverse document frequency over the index (path, summary, symbol
  names). A term found in every file ("module") carries little weight; a rare one
  ("progression") carries a lot.
- Matching is identifier-boundary aware: "rush" matches `RushScene` and `rush/`, but only
  weakly matches `BrushTool`. An identifier word of four or more letters that abbreviates a
  derived query word also matches weakly (`auth` ↔ authentication, `init` ↔ initialization).
- A top-level symbol or file named exactly like a term scores as exact (`middleware()` in
  `middleware.ts`); a method named like a common verb (`finish`) does not.
- Instruction vocabulary (production, responsible, relationship, area, …) is not a code term.

### File relevance

`score = 2·lexical + 3·best symbol + 6·distinct-term coverage (path + summary) + importance`.

For `flow`, `impact` and `editing-prep`, a candidate whose query-relevant callable is
imported **and used** by another candidate is part of the behavior chain; both ends gain
rank. For `editing-prep` and `impact` a type-only import counts too (an interface a module
consumes is a contract). A generic neighbor that only shares a common term gains nothing.

A file stays a primary target only if its score reaches a share of the top score
(navigation 0.5, others 0.35). In a flow whose top file is linked, an unlinked file needs
0.6 of the top score.

### Symbol relevance

Each candidate file ranks its own symbols (`rankFileSymbols`):

1. query terms in the symbol's own name (not the enclosing class name),
2. imported bindings to relevant targets that the symbol body actually uses (call or
   `new`; doubled when the query asks about constructing/consuming/integrating),
3. query terms in the body,
4. behavior over declarations for flow/editing/impact.

Body and binding evidence are density-normalized (`sqrt(40 / lines)`), so a 160-line setup
method that mentions everything in a hub file does not win. A class whose members carry
evidence ranks below those members, so the precise method range is returned instead of the
whole class. A config constant named after the domain (`RUSH`, `CLEANING`) is not
relevance evidence for flow/impact.

The top-ranked target keeps its whole symbol (up to `--max-lines`) as the anchor. Other
long ranges are narrowed to their densest 40-line window of binding uses and query terms.

### Related evidence vs related hints

- `relatedEvidence` = source actually returned. It counts as inspected source.
- `relatedHints` = navigation metadata only. Never cite a hint as inspected source.

Evidence candidates, ranked before the evidence limit is applied:

| relation | direction | when |
|---|---|---|
| `imported-symbol` | outgoing | a binding the primary file imports and uses; strongest when used inside the selected anchor symbol |
| `imported-by` | incoming | impact only: a consumer whose code uses a symbol of the changed file |
| `same-file-symbol` | internal | flow only: a second behavior range of a primary file that also uses a primary binding |

Each evidence item carries a short `reason`, for example
`binding applyCleaningEnd used in CleaningScene.finishCleaning`.

Rules:

- In a flow, a primary file reached only as the callee of another primary file's used
  binding, whose own best range is that callee, is reported as `relatedEvidence` from the
  caller rather than as a separate target.
- Evidence must score at least 0.6 of the strongest edge.
- A non-callable import (constant, enum) is grounded only when the anchor symbol itself
  reads it.
- An import with no lexical relevance that is merely called by the anchor (a UI helper) is
  grounded only when no lexically relevant evidence exists.
- Evidence limits: flow 3, editing-prep 2, impact 2, navigation 1.

### Source budget

All requested ranges (targets and evidence) are collected first. Overlapping ranges for the
same path are removed (a range more than half covered is dropped; otherwise only its
largest uncovered part is kept). The `--max-bytes` budget is then split by weighted
max-min fairness: items that need less than their share are satisfied fully and the
surplus goes to the rest. When a range must be cut, its densest window is kept rather than
its head. The first target has weight 1.5, other targets 1.2, evidence 1.0. Evidence that
would get fewer than 3 lines is dropped instead of returned as a fragment.

### Response shape

```json
{
  "targets": [{ "path": "...", "lines": [362, 407], "symbol": "CleaningScene.finishCleaning", "confidence": 1, "reason": "name matches finish, clean; uses applyCleaningEnd", "source": "..." }],
  "relatedEvidence": [{ "path": "...", "symbol": "applyCleaningEnd", "lines": [31, 38], "relation": "imported-symbol", "direction": "outgoing", "reason": "binding applyCleaningEnd used in CleaningScene.finishCleaning", "source": "..." }],
  "relatedHints": [{ "path": "...", "lines": [28, 47], "symbol": "createDefaultSave", "relation": "imports", "direction": "outgoing" }],
  "groundedFiles": ["..."],
  "intent": "flow",
  "intentDetail": { "confidence": 1, "signals": ["flow:trace"] },
  "depth": 1,
  "more": true
}
```

Scores and scoring matrices are not returned.

## Index change

Type-only imports (`import type { X }`, `import { type X }`) now produce `references`
edges with `importKind: "type"` and confidence 0.6. `INDEXER_VERSION` is 2, so existing
indexes are rebuilt automatically on next access.

## Benchmark intent

Task files may set `category` to `navigation`, `flow`, `impact` or `editing-prep` (legacy
`edit` is still rejected by the read-only runner). An unknown category is an error. A task
without a category is treated as legacy `navigation`, which keeps pre-v0.5.5 task files and
reports meaning what they meant. The category is never inferred from the task id.

Benchmark category and runtime intent are separate fields:

- `category` / `benchmarkCategory`: what the task author says the task is;
- `classifiedIntent`: what StellarCode's classifier infers from the prompt (diagnostic).

The category is never passed to the agent or to StellarCode.

## Report additions

- `categories.{navigation,flow,impact,editing-prep}`: paired runs, input/tool/search/source-byte
  reductions, Stellar grounding and answer rates, expected-file source precision. A category
  without tasks is `status: "n/a"` with null metrics, never zero.
- `taskSummaries[]`: per task, the median across repetitions of input tokens, tool calls,
  search calls, first-relevant time and source bytes for each side, plus the reduction
  between the two medians.
- `taskMedianDelta`: `sumOfMedians…ReductionPct` (each task weighted by its typical size)
  and `medianTask…ReductionPct` (the typical task's improvement).
- Existing aggregate means and gates are unchanged and kept for compatibility.

### Expected-file source precision

```
expectedFileSourcePrecision = unique source bytes read from expectedFiles
                              ---------------------------------------------
                                     all unique source bytes read
```

Reads are merged per file, so overlapping or repeated reads count once. Rows report
`expectedSourceBytes`, `nonExpectedSourceBytes` and `expectedFileSourcePrecision`.

This is a **benchmark proxy for context focus only**. An expected file can contain
irrelevant lines and a non-expected file can be genuinely useful. It is not line-level
semantic correctness and it is not a gate. Rows written before v0.5.5 report it as n/a.

### Gates

Threshold values are unchanged. `navigationInputTokens` is evaluated on navigation-category
paired runs only. Before v0.5.5 every Reefmori task was labelled navigation, so historical
reports effectively measured all tasks there. Re-reporting old JSONL files gives the same
numbers because the old rows still say navigation. When a run has no navigation tasks, the
navigation reduction and gate are `null` (not applicable) instead of a failing 0%.

`filesOpened` is not a success metric on its own: four precise 20-line ranges can be better
than two whole files. Prefer source bytes, round trips, expected-file precision and
correctness.

## Claims

Benchmark results are scoped to the repository, task set, agent and model they were
measured on. For example: on the fixed Reefmori/Claude holdout, v0.5.4 achieved 100%
grounded correctness with 34.2% lower provider input tokens. That is not a universal
token-saving figure.
