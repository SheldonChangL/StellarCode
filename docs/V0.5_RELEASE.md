# StellarCode v0.5 — Multi-Project Core

## Goal

Remove the requirement to `cd` into every repository and run a separate `stellar serve` instance. v0.5 turns StellarCode into one machine-wide project registry and on-demand service.

## Delivered

### Global project registry

`registry.db` tracks:

- project UUID
- display name
- current path
- per-project DB path
- lifecycle status
- last seen/accessed/indexed times
- last indexed Git HEAD
- missing/orphan timestamps
- last lifecycle error

Existing v0.4 registry databases migrate in place by adding columns.

### Single global UI

```bash
stellar ui
```

starts one HTTP server. `/` lists all projects and `/project/<uuid>` opens an indexed project. Project data is lazy-synced immediately before access.

### Global MCP

```bash
stellar mcp
```

works outside a repository. `stellar_projects` discovers registered repos, and all project tools accept `project`, `projectId`, or legacy `projectPath`.

### Lifecycle reconciliation

Normal maintenance requires no commands:

```text
ACTIVE -> IDLE -> MISSING -> ORPHANED
```

The health check reads only registered repository paths. No home-directory traversal occurs.

### Move recovery

The repo-local UUID is path-independent. After moving a repository, any StellarCode command at the new location re-registers the same UUID and keeps the existing per-project index.

### Safe deletion behavior

Deleting a repository does not delete its index. It is marked `missing`, then `orphaned` after the grace period. Orphan cache is safe to reclaim automatically; durable index deletion requires explicit `--purge`.

### Storage management

```bash
stellar gc
stellar remove <project>
stellar remove <project> --purge
stellar gc --purge-orphaned
```

Default GC compacts indexes and removes reconstructable cache for unavailable projects, but never purges indexes.

## Intentionally not included

- login-time OS daemon installation (`launchd`, `systemd`, Windows Service)
- always-on per-project filesystem watchers
- scanning Home for moved repositories
- cloud sync

The v0.5 service is intentionally **on-demand global**. Lazy Git/index checks keep idle projects at zero watcher cost.
