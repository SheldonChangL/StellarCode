# StellarCode v0.6: semantic behavior graph

## Motivation

v0.5.9 showed what first-turn delivery can and cannot do:

- Delivering context in the first turn removes about one model turn, the round trip spent fetching it.
- It does **not** reduce the exploration that follows. Turns with tool use after grounded context were 2.92 for pull versus 3.03 for prefetch.

An agent that still spends about three turns reconstructing the behavior was told *where* the code probably is, but not *how the behavior is wired*.

v0.6 changes what the context carries:

`query → behavior symbol → high-confidence semantic relations → minimal behavior slice → agent`

**Objective:** return the smallest grounded semantic slice that explains the requested behavior well enough to reduce post-context repository exploration. This is not a top-1 file ranking change. Target ranking is unchanged from v0.5.6.

**Invariant:** source is truth; the index is navigation and semantic evidence. Stellar never invents a call relation, infers runtime behavior it cannot see, or claims a complete call graph. An uncertain relation is not an edge.

## Edge model

Edges are stored in the existing `edges` table. `source_id` is a symbol id, or a file id for module-level code; `target_id` is always a symbol id.

| Type | Meaning |
|---|---|
| `CALLS` | The executable symbol (or module) invokes the target function or method. |
| `IMPLEMENTS` | A class explicitly implements an interface, and its same-named method implements the interface method. |
| `REGISTERS` | A function or method known to the index is passed as a call argument (`router.post('/x', handler)`, `bus.on('evt', fn)`), or is decorated by a call-form decorator (`@app.route(…)`). No library or framework name is hardcoded. |
| `CONSUMES` | An imported symbol is used inside an executable symbol without being called: types, contracts, constants, classes. It is recorded only when no `CALLS`, `REGISTERS` or `IMPLEMENTS` edge already links the pair. |

Each edge stores `metadata_json` with:

- `confidence`: `high` or `medium`
- `path`: the source file
- `line`: the evidence line
- `expression`: the callee expression shape, for example `this.repository.save(…)`, with no argument text

Source bodies are never stored.

### Confidence (deterministic)

**high**
- Direct invocation of a local or imported function, including aliases, barrel re-exports and `export *` when exactly one module provides the name
- `this.m()` and `self.m()`
- A receiver whose class is known: a typed parameter, a typed or constructed field, a TS parameter property, `this.x = new C()`, `self.x = C()`, a module-level singleton (`export default new C()`, `export const x = new C()`), or a namespace or module member
- Explicit `implements`
- A callback argument bound to a known function or method

**medium**
- A receiver typed as an **interface**: the edge names the contract method, never a guessed implementation
- A JS constructor field with no type, inferred only when **every** instantiation site in the index passes the same class
- Decorator registration

**No edge** for:
- dynamic or computed calls (`obj[name]()`, `fn()()`)
- untyped receivers without assignment evidence
- unknown modules
- names ambiguous across several `export *` sources
- CommonJS `module.exports` members
- runtime DI containers

Low-confidence semantic edges are never emitted.

## Language support

| Language | Capability | Notes |
|---|---|---|
| TypeScript / JavaScript (`.ts .tsx .mts .cts .js .jsx .mjs .cjs`) | `semantic` | ESM imports, aliases, re-exports, default singletons, typed fields and parameters, parameter properties, `implements`, object-literal methods, class-property arrow methods, interface method signatures |
| Python | `semantic-partial` | `from … import … as …` (including multi-line), module imports, `self.m()`, `self.x = C()`, annotated fields and parameters, module-level instances, call-form decorators. Untyped receivers produce no concrete edge. |
| Others | not indexed | `SUPPORTED_EXTENSIONS` covers only the languages above. `stellar context` reports `semanticCapability` per language in the slice. |

## Parser architecture

See [V0.6_PARSER_DECISION.md](V0.6_PARSER_DECISION.md). The decision was to extend the zero-dependency scanner; Tree-sitter was not adopted.

- **`src/indexer/semantic-extract.js`** extracts per-file facts from text with comments and strings masked:
  - call sites (enclosing symbol, callee chain, identifier arguments)
  - instantiations
  - typed parameters
  - class heritage and fields
  - re-exports and default exports
  - instance and destructured bindings
  - non-call references to imported bindings
  - Python decorators

  It also adds member symbols the v0.5 scanner missed: interface method signatures, class methods with complex parameter lists, class-property arrow methods, and object-literal methods.
- **`src/indexer/semantic-resolve.js`** resolves all files' facts globally and deterministically:
  - binding lookup order: function scope, then module values, then top-level symbols, then imports
  - export resolution: named exports, re-export chains and `export *`
  - receiver typing, member lookup through `extends`, and instantiation-site inference

  Resolution is memoized, depth-bounded at 6 steps, and emits an edge only on a unique result.
- **Index changes:**
  - TS ESM imports of `./x.js` now resolve to `x.ts`.
  - `export … from` is now a module dependency, so barrel files are no longer dead ends.

## Index schema and rebuild

| Item | Change |
|---|---|
| `INDEXER_VERSION` | 2 → **3**. A stored index of any other version is rebuilt deterministically on the next sync (`semanticReindex: true`). An old index is never treated as semantic. |
| `DB_SCHEMA_VERSION` | 3 → **4**. Adds the new table `semantic_facts(file_id, facts_json)`, with a cascade on file delete. |

**Incremental sync:**
- Only changed files are re-parsed. Their facts are replaced.
- Edges, including semantic edges, are re-resolved globally from the stored facts. That is the existing `rebuildEdges` design; resolution takes tens of milliseconds at the sizes measured.
- No LLM is used and maintenance costs zero tokens.

Measured full index on the development repositories (100–1,000 files): 0.4–0.9 s.

## Semantic slice

`src/query/semantic-slice.js`, used by `contextForTask` in compact mode when `depth > 0`. This covers both `stellar context --compact --depth 1` and MCP `stellar_context` with `withSource`. They share one implementation, so their output is identical by construction and by test.

**Seeds** are the context targets' symbols:
- A container (class, interface, object singleton) stands for its members.
- For **impact**, a method target stands for its owning class or singleton.
- A target without a symbol stands for its file's symbols.

**Traversal** follows only stored edges, by intent:

| Intent | Relations followed | Max edges |
|---|---|---|
| navigation | incoming `CALLS`/`REGISTERS`, depth 1 (who wires and uses the owner; callees stay hints) | 3 |
| flow | outgoing `CALLS`/`REGISTERS` to depth 2; incoming `REGISTERS`; the unique caller | 6 |
| impact | incoming `CALLS`/`CONSUMES`/`IMPLEMENTS`/`REGISTERS`, depth 1 | 8 |
| editing-prep | outgoing `CALLS`/`CONSUMES`; incoming `CALLS`; `IMPLEMENTS` both ways; depth 1 | 6 |

**Ordering is structural.** Edges are ranked by:
1. confidence
2. which target they start from (the first target is the owner)
3. depth
4. cross-file over same-file
5. utility penalty: callee fan-in, so a helper called from everywhere ranks low
6. chain continuation

Lexical relevance only breaks ties. Edges inside one seed container are dropped, and test files are never neighbors.

**Grounding:**
- A callee or implementation is grounded by its symbol range.
- A caller or consumer is grounded by a window around the evidence line inside its symbol.
- Each range is included once: it is subtracted against ranges already taken.
- The ranges share the `--max-bytes` budget through the existing max-min fair allocation. The default budget is 20,000 bytes since v0.6.2 (12,000 before); bytes the allocation leaves unused grow narrowed ranges back toward their symbol bounds.
- A compact response is serialized on one line (`--compact --json`) and held under 29,000 bytes: evidence is dropped from the end, the same-file declarations first, and `more` is set. Agent harnesses replace a larger tool result with a short preview.
- Since v0.6.2, bytes still unused after that attach same-file declarations as `relatedEvidence` entries with `relation: "same-file-declaration"` and `direction: "internal"`: module-level bindings and small functions or constants that the returned ranges name, followed two hops, with the comment directly above. At most 40 lines per file and 6 entries per response. They are read from live source at query time; nothing is added to the index.
- Semantic evidence comes first. Lexical related evidence fills only what the slice did not already ground.

**Payload** (backwards compatible):
- `targets`, `relatedEvidence`, `relatedHints`, `groundedFiles` and `more` keep their meaning.
- `relatedEvidence[].relation` keeps the v0.5 vocabulary (`imported-symbol`, `imported-by`, `same-file-symbol`). A slice item adds `semantic: {relation, confidence}`.
- New fields:
  - `semanticEvidence: [{relation, direction, from:{path,symbol,line}, to:{path,symbol}, confidence, depth}]`
  - `semanticHints` (v0.6.1, present only when non-empty): relations the traversal admitted but the edge budget left out, in the same shape as `semanticEvidence`. At most `maxEdges` more. No source is attached and nothing is grounded, so they are navigation metadata, never source-of-truth.
  - `semanticCapability: {language: capability}`

**Switch.** `STELLAR_SEMANTIC_SLICE=0` (or `{semantic:false}`) turns the slice off. The benchmark's `stellar-lexical` condition uses this to compare the same runtime, index, targets and prompt with and without the slice.

## Body evidence in file ranking (v0.6.2)

Until v0.6.2 a file was a candidate only when its path, summary or symbol names carried a task term. A file whose behavior sits in its body (a middleware configured inline, a component whose logic lives in a hook) scored zero and never reached ranking or seed selection.

- At query time the indexed source is read once from the working tree. Nothing about bodies is stored in the index.
- A task term counts for a file when an identifier word or a comment word in the body starts with it.
- Each matched term contributes its rarity: 1 when one file has it, falling linearly to 0 once 30% of the files have it.
- A file whose summed rarity reaches 1.5 gains 10 points per unit in the file ranking. One exact symbol-name match is worth up to 30, so a file needs several rare body terms to pass a name match.
- The scan is skipped when the indexed source exceeds 16 MB, and files over 400 KB or marked generated are left out. Ranking then works on names alone, as before.
- Cost on the largest test repository (480 files, 2.2 MB): about 0.1 s per query.

## Known limitations

- **Not resolved:**
  - dynamic dispatch, reflection, computed property calls (`obj[name]()`)
  - runtime DI container resolution, monkey patching, framework magic (decorator-registered routes are recorded as medium `REGISTERS` only)
  - untyped ambiguous receivers, including Python `self.repo` without assignment evidence
- **Not supported:**
  - CommonJS `module.exports = …` members (`require` binds the module; member exports are not resolved)
  - destructuring from anything other than a module, instance or object binding
  - returned values (`const repo = makeRepo()` gives no type)
- **Interface dispatch** is never resolved to an implementation. The slice shows the contract method; implementations remain navigation through `IMPLEMENTS`.
- **The slice starts from the v0.5.6 targets.** When lexical target selection picks the wrong behavior owner, the slice is correct for that owner but does not contain the requested chain. On the development repositories, 46 of 106 tasks had a correct top target. This is the main capability gap v0.6 does not address.
- **Regex extraction misses some shapes:** chained calls on call results, JSX element usage as calls, calls inside template literal interpolations (masked) and generated code. A missed fact means no edge, never a wrong one.
