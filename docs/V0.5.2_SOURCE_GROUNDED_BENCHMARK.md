# StellarCode v0.5.2 — Source-Grounded Token Benchmark

v0.5.2 fixes the failure mode exposed by the first real Codex benchmark: StellarCode reduced discovery tokens dramatically, but the agent answered from index metadata without opening repository source. That is not an acceptable optimization.

The v0.5.2 rule is:

> StellarCode locates the code. Repository source proves the answer.

## New source-grounding flow

`stellar context` now returns a bounded read plan for each primary match:

```json
{
  "path": "src/actions/auth.ts",
  "symbols": [{"qualifiedName":"login","lines":[47,116]}],
  "read": {
    "required": true,
    "lines": [41,126],
    "command": "stellar source \"src/actions/auth.ts\" --lines 41:126 --json"
  }
}
```

The agent must then read source with either its native file reader or:

```bash
stellar source src/actions/auth.ts --lines 41:126 --json
```

`stellar source` returns only the requested bounded range with line numbers. It does not copy source into the index.

## Three-layer correctness

Every benchmark run now records:

1. **Discovery correctness** — did the run locate an answer-key file?
2. **Source grounding** — did the run actually read an answer-key source file/range?
3. **Answer correctness** — did the final structured answer identify an answer-key file?

A fourth metric, **Grounded Success**, is true only when the answer is correct **and** source grounding passed.

This prevents a run like this from passing:

```text
Stellar context -> metadata summary -> final answer
```

Even if the final file name happens to be correct.

## Acceptance gate

The v0.5.2 report requires all of:

| Metric | Gate |
|---|---:|
| Overall input tokens | >= 20% reduction |
| Navigation input tokens | >= 50% reduction |
| Tool calls | >= 40% reduction |
| Median time to first relevant source read | >= 40% reduction |
| Stellar source-grounding rate | >= 95% |
| Answer correctness delta | no worse than baseline by >5 points |
| Grounded-success delta | no worse than baseline by >5 points |

The gate is intentionally strict. A token reduction with missing source grounding is `NOT YET PROVEN`.

## Upgrade note

v0.5.2 fixes JS/TS class-method line ranges used by the read plan. After upgrading from v0.5.1 or older, run one full scan per benchmark repository:

```bash
stellar scan
```

This is a deterministic rebuild and consumes no LLM tokens.

## Measurement procedure

### 1. Install v0.5.2

```bash
cd StellarCode_v0.5.2
npm link
```

### 2. Refresh the benchmark repository index once

```bash
cd /path/to/your/repository
stellar scan
```

### 3. Verify source grounding manually

```bash
stellar context "Find the production login implementation" --json
```

Choose the primary production file and run the returned `read.command`, for example:

```bash
stellar source src/actions/auth.ts --lines 41:126 --json
```

Confirm that the excerpt contains the implementation you expect.

### 4. Reuse the existing answer-key task file

You do **not** need to run `stellar benchmark init` again if `.stellar/benchmark/tasks.json` already exists.

For the first debug run, one known task is enough. For a product claim, curate 10–20 tasks from maintainers, bug history, tests, or known system behavior.

### 5. Run exactly the same A/B again

```bash
stellar benchmark run \
  --agent codex \
  --mode both \
  --repeat 3
```

Do not change the task, model, repository commit, or answer key when comparing v0.5.1 and v0.5.2 behavior.

### 6. Open the generated report

macOS:

```bash
RUN_DIR=$(ls -td .stellar/benchmark/runs/*-codex | head -1)
open "$RUN_DIR/report.html"
```

Or inspect JSON:

```bash
cat "$RUN_DIR/report.json"
```

### 7. Read the result in this order

First require:

```text
Stellar Discovery          100%
Stellar Source Grounding   100%   (>=95% for larger sets)
Stellar Answer Correctness 100%
Stellar Grounded Success   100%
```

For a one-task debug run, all four should normally be 100%.

Only then evaluate savings:

```text
Input token reduction
Navigation input token reduction
Tool-call reduction
Time to first relevant source
```

The important comparison is **tokens saved while Grounded Success stays equal to baseline**.

## How to interpret the first one-task rerun

A healthy result could look like:

```text
Discovery                 100% -> 100%
Source grounding          100% -> 100%
Answer correctness        100% -> 100%
Grounded success          100% -> 100%
Input tokens              -30% to -50%
```

The previous v0.5.1 result (`-64% tokens`, but Stellar grounded success `0%`) is not a valid savings claim.

If v0.5.2 returns correctness/grounding to 100% and still saves meaningful input tokens, the core hypothesis becomes much stronger.

## When the one-task rerun passes

Expand to:

- 10–20 real tasks;
- at least 3 repetitions each;
- preferably 3 repositories;
- then repeat on both Codex and Claude.

Do not generalize a single repository or single task percentage to all coding work.
