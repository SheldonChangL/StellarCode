# StellarCode v0.5.1 — Token Benchmark Harness

v0.5.1 exists to answer one question with measured data:

> Does StellarCode reduce the tokens a coding agent consumes while preserving repository-navigation correctness?

## What is measured

For every fresh agent run the harness records:

- effective input tokens;
- uncached/cached/cache-write input tokens when the agent exposes them;
- output and reasoning-output tokens when available;
- tool calls;
- broad search calls;
- unique source files opened;
- estimated source bytes opened;
- time to first answer-key file read;
- exit status;
- answer-key correctness;
- cost when the agent exposes it.

Claude and Codex usage are normalized separately. Claude's effective input count includes normal + cache creation + cache read input tokens. Codex `input_tokens` is treated as the total input count while its cached count is reported as a subset.

## Fair A/B isolation

Every task/condition runs in:

- a new agent process/session;
- a fresh detached Git worktree at the same HEAD;
- an isolated StellarCode data/cache directory;
- the same task prompt and output contract;
- user-configured MCP servers disabled/ignored for the benchmark agent where the CLI supports it.

The only intentional difference is repository discovery:

- **Baseline**: a PATH shim disables `stellar`; normal search/read tools are used.
- **Stellar**: the PATH shim points to the packaged StellarCode version and the prompt requires `stellar context` before broad search.

Codex runs use ephemeral/ignore-user-config/ignore-rules isolation. Claude runs exclude setting sources, use a strict empty MCP config, and disable claude.ai MCP connectors.

Any StellarCode navigation rule previously appended to `AGENTS.md` or `CLAUDE.md` is removed only inside the temporary benchmark worktree so the baseline is not contaminated.

Index construction happens before the timed agent run. It is deterministic/zero-token and represents the already-indexed normal StellarCode workflow. The report is therefore a token/navigation benchmark, not a first-install benchmark.

## 1. Create an answer-key task set

Inside an initialized repository:

```bash
stellar benchmark init
```

Edit:

```text
.stellar/benchmark/tasks.json
```

The generated examples are disabled. Replace them with real tasks such as:

```json
{
  "version": 1,
  "tasks": [
    {
      "id": "auth-login",
      "enabled": true,
      "category": "navigation",
      "prompt": "Find the production login implementation and explain where credentials are verified.",
      "expectedFiles": ["src/actions/auth.ts"],
      "expectedMatch": "any"
    }
  ]
}
```

`expectedFiles` is the hidden answer key. It is never included in the agent prompt.

For a credible claim, use at least 10–20 real tasks covering different modules. Avoid tasks generated from StellarCode search results; curate them from known behavior, bug history, tests, or maintainers' knowledge.

## 2. Check agent availability

```bash
stellar benchmark doctor --agent all
```

or:

```bash
stellar benchmark doctor --agent claude
stellar benchmark doctor --agent codex
```

The doctor also checks whether the installed CLI exposes the flags needed for isolated telemetry runs. The harness does not log in for you. Run the agent normally first if authentication is required.

## 3. Run paired A/B

Codex:

```bash
stellar benchmark run --agent codex --mode both --repeat 3
```

Claude Code:

```bash
stellar benchmark run --agent claude --mode both --repeat 3
```

Optional model pinning:

```bash
stellar benchmark run --agent codex --mode both --model MODEL_NAME --repeat 3
```

`--repeat 3` is recommended because agent runs are stochastic. Baseline/Stellar ordering alternates by task/repetition to reduce order bias.

Runs are stored under:

```text
.stellar/benchmark/runs/<timestamp>-<agent>/
├── baseline.jsonl
├── stellar.jsonl
├── manifest.json
├── report.json
└── report.html
```

## 4. Read the result

The automatic pass gate requires all of:

| Metric | Gate |
|---|---:|
| Overall input tokens | >= 20% reduction |
| Navigation input tokens | >= 50% reduction |
| Tool calls | >= 40% reduction |
| Median time to first relevant file | >= 40% reduction |
| Correctness | Stellar no worse than baseline by >5 percentage points |

Every run must have an answer key before correctness is considered verified. If answer keys are missing, the report says `NOT YET PROVEN` even when tokens decrease.

## Report an existing run

```bash
stellar benchmark report baseline.jsonl stellar.jsonl \
  --json-out report.json \
  --html report.html
```

## Interpretation

A result such as:

```text
Overall input tokens       -28%
Navigation input tokens    -61%
Tool calls                 -54%
Time to relevant file      -47%
Correctness                unchanged
```

supports the claim that StellarCode reduces repository-discovery cost for that repository/task set/agent/model.

Do not generalize one repository's percentage to all coding tasks. Editing-heavy tasks that must read large source files will naturally save less than navigation-heavy tasks.

## Costs and safety

The harness launches real Claude/Codex sessions and may consume subscription/API quota. Benchmark tasks are currently forced to read-only agent modes and temporary worktrees; v0.5.1 is designed primarily for repository-navigation measurement rather than edit-quality benchmarking.
